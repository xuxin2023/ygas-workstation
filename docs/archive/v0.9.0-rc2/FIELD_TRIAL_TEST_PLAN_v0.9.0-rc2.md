## 4. 试验顺序与安全原则

1. 先模拟器。任何涉及恢复失败、`FFF` 风险、只读锁、导出口径的高风险验证，先在模拟器跑通一次。
2. 再单设备。真实仪器验证优先在单设备、明确目标设备 ID 的环境中执行。
3. 再隔离总线。若必须验证总线行为，先切到与生产现场隔离的总线或明确影响范围的试验总线。
4. 最后才允许多设备总线。多设备总线验证应放在全部单设备与隔离验证完成之后。

- 未经现场负责人确认，不得在多设备生产总线上执行 `FFF` 写命令。
- 能单设备就不广播。
- 目标不明确时不得默认 `FFF`。
- 任何可能改设备状态的动作前，必须再次确认当前目标设备、只读锁状态、会话模式和总线范围。
- 如现场负责人要求停止试用，应立即停止，不得继续做“再试一次”。

## 5. FFF 广播现场安全限制

- 不得在未隔离的多设备生产总线上直接验证 `FFF` 写命令。
- `FFF` 写命令必须经过现场负责人确认，且要记录确认时间、负责人姓名与截图。
- 验证优先使用模拟器或单设备隔离环境。
- 若仅需验证单设备链路，不得以 `FFF` 代替明确设备 ID。
- 任何 `MODE2 + FFF` 或等价高风险写命令，未完成强确认前不得发送。
- 若目标不明确却尝试使用 `FFF`，本场景直接判定为失败，并立即留证。

## 6. 禁止事项

- 禁止在未确认目标设备时执行写命令。
- 禁止在多设备生产总线上直接试 `FFF` 写命令。
- 禁止跳过试验后状态恢复检查。
- 禁止未导出会话包就结束失败场景。
- 禁止手工修改日志后提交问题单。
- 禁止混用不同 SHA256 的包做同一轮试用。

## 7. 通用留证要求

### FT-02 10Hz 自动上传

**目标**

验证 10Hz 主动上传下的长时间采集、实时曲线刷新、丢帧统计和会话包导出完整性。

**前置条件**

- 已通过 FT-01。
- 设备支持 10Hz 主动上传。
- 现场允许连续运行 30 分钟。
- 已确认本次试验的期望接收频率为 `10Hz`。

**操作步骤**

1. 开启主动上传并记录实际开始时间。
2. 连续采集 30 分钟。
3. 观察实时曲线是否持续刷新。
4. 记录采集期间的丢帧统计、是否出现长时间停顿、明显跳变或刷新冻结。
5. 采集结束后导出会话包。
6. 检查导出目录中的 `structured_data.csv` 与 `session_summary.json`。
7. 记录以下量化字段：
   - `expected_frame_count`
   - `structured_frame_count_exported`
   - `drop_frame_rate`
   - `max_consecutive_no_data_gap`
   - `raw_rx_count_total`
   - `structured_started_at`
   - `structured_ended_at`

**量化记录口径**

- 30 分钟、10Hz 理论帧数约为 `18,000` 帧。
- `expected_frame_count = 30 x 60 x 10 = 18,000`。
- `drop_frame_rate = 1 - structured_frame_count_exported / expected_frame_count`。
- `max_consecutive_no_data_gap` 以秒记录，来自界面观察或日志复盘均可。
- 丢帧率和最大无数据间隔阈值为 `rc2` 默认验收阈值；如现场链路条件特殊，可由现场负责人在试验前记录并调整阈值，但必须说明原因。

**验收标准**

- 必须记录 `expected_frame_count`，本场景默认值应为 `18,000`。
- 必须记录 `structured_frame_count_exported`，且该值应大于 `0`。
- `drop_frame_rate <= 1.0%` 判为通过；`1.0% < drop_frame_rate <= 5.0%` 判为阻塞并留证；`drop_frame_rate > 5.0%` 判为失败。
- `max_consecutive_no_data_gap <= 1.0s` 判为通过；`1.0s < gap <= 3.0s` 判为阻塞并留证；`gap > 3.0s` 判为失败。
- `timestamp` 应单调递增，不得出现倒退；如出现倒退、重复或明显乱序，判为失败。
- `raw_rx_count_total` 应大于或等于 `structured_frame_count_exported`。
- `structured_started_at` 与 `structured_ended_at` 应覆盖本次试验时段；与人工记录的开始/结束时刻偏差不应超过 `5s`。
- 会话包中应导出 `structured_data.csv`，而不是仅有 `recent_structured_data.csv`。
- `session_summary.json` 中的 `structured_export_scope` 必须为 `full`。
- 如果导出不是 `full`，必须判为失败或阻塞并留证，不得判为通过。

### FT-05 恢复失败场景

**目标**

**前置条件**

- 使用可控方式制造恢复失败，优先使用模拟器、隔离设备或 ACK 超时方式；不得通过不明确广播方式诱发失败。

**操作步骤**

1. 在主动上传开启状态下执行 `GETCO` 暂停上传后读取。
2. 在恢复阶段模拟或制造 `SETCOMWAY=1` 失败。
3. 观察 UI 状态和结果提示。
4. 确认界面是否提供 `重试恢复主动上传`、`保持关闭`、`查看命令日志`。
5. 点击 `保持关闭`。
6. 导出 `command_log.csv`、`parameter_change_journal.csv/json` 和 `session_summary.json`。

**验收标准**

- UI 显示 `恢复失败`。
- UI 中可见 `重试恢复主动上传`、`保持关闭`、`查看命令日志`。
- 详情区应能看到 `恢复主动上传失败` 相关提示。
- 点击 `保持关闭` 后，`command_log.csv` 中能看到 `保持主动上传关闭`。
- `parameter_change_journal.csv/json` 中应保留本次恢复失败及用户选择保持关闭的记录。
